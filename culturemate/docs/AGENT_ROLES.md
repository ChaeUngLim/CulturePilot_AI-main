# 문서 1 — 멀티에이전트 역할 정의

> **기획안(MOBIDIC)의 Agent 4역할을 설계 9종으로 나누고, 각 Agent의 책임·입출력·관심사를 계약으로 고정한다.**
> 최종 구현 방향의 기준은 [PLANNING.md](PLANNING.md) — 이 문서는 그 §3.1(멀티 에이전트 구조)과
> §3.2(데이터 파이프라인)를 설계 언어로 옮긴 것이다.
>
> 이어지는 문서 — 협업 순서와 데이터 흐름은 [AGENT_WORKFLOW.md](AGENT_WORKFLOW.md),
> 실행·배포 구조는 [SYSTEM_C4.md](SYSTEM_C4.md).
>
> **작성 원칙 — 소스가 근거다.** 이 문서의 모든 파일·함수·상수는 작성 시점에
> `culturemate/app/` 에서 확인한 것이다. 코드에서 확인되지 않는 것은 ⬜ 로 남긴다.

- 검증 기준: `langgraph 1.2.10` · `langchain-core 1.5.3` · `fastapi 0.141.1` · `pydantic 2.13.4`
- 대조한 소스: 메인 그래프 **11 노드**(서브그래프 4 + 조율 7) · 라우트 **7종** · 검증 **6종** · 엔드포인트 **23개**

## 0. 한 문장

> **아홉 개의 전문 Agent가 공유 State 하나에 각자의 산출물을 쌓고,
> 다음 Agent는 그 State를 읽는다. Agent끼리는 서로를 호출하지 않는다.**

이 한 문장이 이후의 모든 설계 결정을 만든다. 서로 호출하지 않기 때문에
하나가 실패해도 나머지가 돌고, 순서를 바꿔도 계약이 깨지지 않는다.

## 1. 왜 4종이 아니라 9종인가

### 1.1 나누는 기준 — «기능이 다른가»가 아니라 «따로 실패할 수 있는가»

기획안 3.1은 **역할 이름**을 정했다. 설계는 거기서 한 걸음 더 나가
**«한 Agent가 두 가지 책임을 지고 있지 않은가»** 를 따진다. 판단 기준은 셋이다.

| 기준 | 물음 | 예 |
|---|---|---|
| **실패 독립성** | 이것만 죽어도 나머지가 성립하는가 | Culture(A3)가 외부 쿼터로 비어도 Preference(A2)의 기록으로 일정이 나온다 |
| **관심사 계층** | 외부를 알아야 하는가, 순수 계산인가 | Planner(A5)는 외부를 모른다 · Route(A6)는 경로 API를 쓴다 |
| **변경 축** | 무엇이 바뀌면 이것만 고치면 되는가 | 경로 제공자가 바뀌면 A6만, 검증 기준이 바뀌면 A4만 |

**셋 중 하나라도 갈리면 나눈다.** 나누지 않으면 «탐색이 실패했는데 일정도 안 나온다»
같은 결합이 생기고, 그 결합은 코드가 아니라 **응답 품질**로 사용자에게 나타난다.

### 1.2 기획안 4역할 → 설계 9 Agent 도출표

| 기획안 3.1 | 하는 일 (기획안 원문 요약) | 설계 | 판단 | 나눈 근거 |
|---|---|---|:--:|---|
| **Router** | 요청 유형을 판별해 필요한 Agent만 호출 | `Router(A1)` | 유지 | 책임이 하나다 — 나눌 이유가 없다 |
| **Search Agent** | 공공 문화 API와 개인 아카이브를 **동시에** 조회 | `Preference(A2)` · `Culture(A3)` | 분할 ×2 | «동시에»가 곧 두 갈래다. 실제로도 병렬 슈퍼스텝이며, 하나가 비어도 다른 하나로 답한다 |
| **Validation Agent** | 공식 홈페이지 교차 확인 · **«확인 실패»는 추정치를 쓰지 않는다** | `Verifier(A4)` · `Guardian(A8)` | 분할 ×2 | «장소가 실재하는가»(탐색 단계)와 «이 일정이 성립하는가»(편성 뒤)는 시점도 입력도 다르다 |
| **Planning Agent** | 시간·날씨·거리로 순서 계산 · 제약 위반은 사유와 함께 반려 | `Planner(A5)` · `Route(A6)` · `Gap(A7)` | 분할 ×3 | 순서 결정(순수 계산) · 이동 측정(외부 호출) · 빈틈 채우기(팬아웃)는 실패 양상이 전부 다르다 |
| **Memory Agent** ※ | 3.1 «되돌림» · 3.2 «피드백 회귀»로 **기능만 서술됨** — 역할 이름은 없었다 | `Memory(A9)` | 신설 | 선순환의 «04 기록 → 05 분석»을 실행할 주체가 필요하다. 기획안이 가장 강하게 약속한 차별점(수정 행동 학습)의 실행자다 |

> **※ Memory Agent 는 기획안 3.1 의 역할 4종 표에 이름이 없다.** 기획안은 그 기능을
> «되돌림»(3.1)과 «피드백 회귀»(3.2)로 **서술만** 했고, 역할로 세우지 않았다.
> 설계가 이름을 붙였으므로 «신설»로 표기한다 — 없던 기능을 더한 것이 아니라,
> **주인이 없던 기능에 주인을 지정한 것**이다.

**4 → 9 = 8 + 1.** 기획안의 네 역할을 여덟으로 나누고, 이름이 없던 하나를 세웠다.
늘어난 넷은 새 기능이 아니라 **기존 책임의 분리**이고, 나머지 하나는 **이름의 부여**다.
기획안이 약속한 범위는 그대로이고, 실패 지점만 잘게 나뉘었다.

| 기획안 역할 | → | 설계 |
|---|:--:|---|
| Router | 1 | `Router(A1)` |
| Search Agent | 2 | `Preference(A2)` · `Culture(A3)` |
| Validation Agent | 2 | `Verifier(A4)` · `Guardian(A8)` |
| Planning Agent | 3 | `Planner(A5)` · `Route(A6)` · `Gap(A7)` |
| **Memory Agent** (신설) | 1 | `Memory(A9)` |

### 1.3 Agent로 세지 않은 것

결정을 하지 않으면 Agent가 아니다. 아래 셋은 이 문서의 9종에 들어가지 않는다.

| 대상 | 무엇인가 | 어디에 있나 |
|---|---|---|
| **캘린더** (UR-28) | 저장된 일정을 날짜로 조회하는 **읽기 화면** | `GET /plans/{user_id}` · `(tabs)/calendar.tsx` |
| **도구 계층** | 외부 API 어댑터 — 타임아웃·캐시·폴백·응답 정규화 | `app/tools/` |
| **큐레이션** | 대화 흐름 밖에서 도는 배치 성격의 집계 | `app/memory/curation.py` |

## 2. Agent 9종 — 책임 계약표

각 Agent는 **«입력을 받아 정해진 산출물을 공유 State에 남긴다»** 는 계약만 지킨다.

| # | Agent | 책임 — 한 문장 | 입력 | 출력 (State 채널) | 관심사 | 구현 |
|:--:|---|---|---|---|:--:|---|
| A1 | **Router** | 발화를 실행 계획으로 바꾼다 | 자연어 발화 · 화면 입력값 · 취향 프로필 | `request_type` · `plan_flags` · `conditions`(좌표 확정) | 응용 | `graph/router/` (6모듈) |
| A2 | **Preference** | 과거 기록에서 취향과 불편을 뽑는다 | `user_id` · `conditions` | `taste_profile` · `archive_hits[]` · `evidence[]` | 응용 | `subgraphs/archive.py` · `memory/{retriever,profile}.py` |
| A3 | **Culture** | 조건에 맞는 장소 후보군을 만든다 | `conditions`(지역·날짜·좌표·관심사) | `candidates[]` · `evidence[]` | 응용 | `subgraphs/discovery.py` · `tools/{culture_api,websearch,local_catalog,region}.py` |
| A4 | **Verifier** | 후보가 실재하는지 공식정보로 가른다 | `candidates[]` 상위 12개 | `verifications[]` · `place_diffs[]` · `evidence[]` | 응용 | `discovery.verify_node` · `tools/verify.py` |
| A5 | **Planner** | 순서·시각·체류시간을 확정한다 | 후보 · 취향 · 이동행렬 · 운영시간 · 날씨 | `itinerary`(항목별 도착·출발·이유) | 도메인 | `subgraphs/itinerary/{context,schedule,placement,dwell,notes}.py` |
| A6 | **Route** | 구간 이동시간과 수단을 확정한다 | 확정된 항목 좌표쌍 · 선호 수단 · 주차 사정 | 구간 `travel_min`·`mode`·`travel_path` · `transport_mix` | 인프라 접점 | `itinerary/{legs,routes}.py` · `tools/{maps,routing}.py` |
| A7 | **Gap** | 식사 자리를 잡고 빈 시간을 채운다 | 편성 중 일정 · `gaps[]` · 앵커 좌표 | `nearby[]` · 삽입된 일정 항목 | 도메인 | `itinerary/gaps.py` · `placement._meal_slot()` |
| A8 | **Guardian** | 일정의 문제를 찾아 사용자에게 확인받을 것만 고른다 | 확정 일정 · `archive_hits[]` · 날씨 | `issues[]` · `advisories[]` · 정지 신호 | 응용 | `subgraphs/validation.py` · `nodes.human_review` |
| A9 | **Memory** | 이번 행동에서 배울 것을 남긴다 | 사용자 선택 · 일정 diff · 방문 기록 | `plan_edits` 행 · 갱신된 `taste_profiles` | 응용 | `nodes.persist` · `memory/{writer,profile}.py` |

**관심사 4계층** — UI · 응용(조율) · 도메인(순수 계산) · 인프라(바깥과 닿는 것).
A5 · A7 은 **외부 호출이 없다.** 그래서 도메인이고, 그래서 재현 가능하다.
A6 은 도메인 규칙(주차·환승 환산)을 갖지만 실측을 위해 도구 계층에 닿으므로 접점에 둔다.

## 3. Agent별 상세

각 항목은 **처리 순서 · 불변 규칙 · 실패 시 동작**을 함께 적는다.
불변 규칙은 대부분 실제로 한 번씩 깨져 본 자리다.

### A1 · Router — 요청 해석

| | |
|---|---|
| **입력** | 자연어 발화, 화면 칩(출발/도착/시각/이동수단/지역), 저장된 취향 프로필 |
| **출력** | `RequestType`(7종) · `PlanFlags` · `TripConditions`(**좌표 확정 포함**) |
| **구현** | `graph/router/__init__.py`(라우팅 표·`classify`·`fan_out`) · `rules.py` · `detect.py` · `endpoints.py` · `timeparse.py` · `enrich.py` |

```
① 규칙 추출     _rule_conditions()   정규식 — 지역·날짜·시각·수단·개수·체류
② LLM 보강      structured("router") 규칙이 부족할 때만
③ 규칙 보정     _merge_rules()       LLM이 놓친 빈칸을 규칙이 채운다
④ 화면값 덮기   _apply_override()    발화가 화면 잔재보다 세다
⑤ 취향 반영     _apply_taste()
⑥ 좌표 확정     _resolve_places()    출발·도착·지역 → GeoPoint
```

- **불변 1 — 방금 한 말이 화면에 남은 이전 값을 이긴다.** ④가 없으면 이전 화면의 출발지가 방금 말한 출발지를 덮는다.
- **불변 2 — 좌표 확정은 여기서 한다.** 서브그래프가 `conditions`를 제자리에서 고쳐도 출력 스키마에 없으면 부모로 돌아오지 않는다. 의미상으로도 위치 해석은 «요청을 이해하는 일»이다. 출력 스키마는 이 문제와 **병렬 키 충돌**을 함께 막는다 — [그림](diagrams/parallel-key-conflict.svg) · [AGENT_WORKFLOW §4.0](AGENT_WORKFLOW.md).
- **불변 3 — 현재 위치는 출발지가 아니다.** 말한 출발지 > 말한 지역의 중심 > GPS 순.
- **실패 시** — LLM이 죽어도 규칙 결과로 진행한다. 규칙이 요청 유형·장소·시각을 **모두** 잡았을 때만 LLM을 건너뛴다(`_rules_suffice`).

### A2 · Preference — 과거 경험 조회

| | |
|---|---|
| **입력** | `user_id` · `TripConditions` |
| **출력** | `TasteProfile` · `archive_hits[]` · `evidence(kind="archive")` |
| **저장소** | `visits` · `plan_edits` · `experience_embeddings`(pgvector 1024차원) · `taste_profiles` · `preference_cards` |

```
plan_facets → ⟨Send 팬아웃⟩ facet_search ×3 → fuse_rerank → extract_relevant
```

**3 facet 병렬** — 단일 질의로는 세 종류 이웃을 동시에 못 잡는다.

| facet | 잡는 것 |
|---|---|
| `similar_place` | 비슷한 장소·지역·카테고리 |
| `context_match` | 동행자·이동수단·계절이 비슷했던 상황 |
| `friction_edit` | 불편했던 경험과 그때 한 수정 |

**학습 신호 두 갈래** — 방문 기록(`rebuild_profile`)과 수정 행동(`extract_edit_signals`).
별점은 사후 합리화가 섞이지만 **수정 행동은 그 순간의 실제 선택**이다.

**프로필이 개입하는 두 지점**

| 값 | 쓰이는 곳 | 방식 |
|---|---|---|
| `preferred_categories` · `indoor_bias` | 후보 점수 | `final_score = 0.6×relevance + 0.4×personal_score` |
| `avg_dwell_min` | 체류시간 | 사용자가 말하지 않았을 때만 배율 보정(0.7~1.6 상한) |

- **불변 1 — 경고 카드를 만들지 않는다.** 검색과 «알려야 함»의 판정은 다른 일이다. 카드는 A8 한 곳에서만 만든다(두 곳에서 만들면 같은 사안이 카드 두 장이 된다).
- **불변 2 — 등록한 취향이 다녀온 곳을 이기지 않는다.** 카드 기여분은 `_CARD_CAP=0.30` 으로 자른다.
- **불변 3 — 재집계가 카드와 수정 행동을 되읽는다.** 재집계는 전량 재계산이라, 빼면 방문 **한 건**이 들어온 순간 등록해 둔 취향이 지워진다.
- **실패 시** — 개인화만 꺼지고 일정은 성립한다. 임베딩 호출까지 가드 안에 둔다.

### A3 · Culture — 후보 탐색

| | |
|---|---|
| **입력** | `TripConditions` |
| **출력** | `candidates[]` · `evidence(kind="web")` |
| **소스 4종** | 내장 카탈로그 · 기간형 행사(KCISA) · 상시 문화공간(공공데이터포털+네이버) · 웹검색(Tavily→Exa) |

```
search_catalog   ┐
search_events    ├→ normalize → ⟨조건부⟩ verify → classify
search_always_on │
search_web       ┘
```

**관문 4개 (`normalize`)** — 이 순서로 후보를 거른다.

1. **좌표가 없으면 후보가 아니다.** 이름이 아니라 좌표가 자격이다. 이 관문이 없으면 블로그 글 제목이 장소로 일정에 들어간다.
2. **시·도 판정** (`tools/region.py`, UR-18). 요청한 시·도가 **아니라고 확인된** 후보만 버린다. 모르는 후보는 통과시킨다.
3. **거리 상한** `MAX_ANCHOR_KM = 60.0`. 행정구역을 모르는 후보를 받는 보조 관문.
4. **기간·제외어 필터.**

통과한 뒤 말한 구(區)에 있는 후보에 `REGION_BONUS = 0.15` 를 얹는다 — **자르지 않고 가점만** 준다(구 경계 ≠ 생활권).

- **불변** — 같은 장소가 여러 소스에서 오면 **정보가 더 풍부한 쪽**을 남기고 점수는 max로 병합한다.
- **실패 시** — 내장 카탈로그가 받쳐 결과가 0건이 되지 않는다.

### A4 · Verifier — 공식정보 대조

| | |
|---|---|
| **입력** | `candidates[]` 중 상위 `verify_top_k = 12`(`candidate_pool = 60` 중) |
| **출력** | `verifications[]` 3분류 · `place_diffs[]`(재방문 변경점) · `evidence(kind="official")` |

```
verified     공식 출처와 일치     → 그대로
needs_check  정보 부족            → 점수 0.8배 + «확인 필요» 표시
excluded     불일치·종료 확인     → 제외
```

- **불변 1 — 모르면 버리지 않고 «확인 필요»로 남긴다.** 소규모 공방·독립서점은 공식 정보가 원래 부실하다. 전부 떨구면 상시 문화공간 추천이 통째로 사라진다. **기획안 3.1의 «확인 실패는 추정치를 쓰지 않는다»가 이 규칙이다.**
- **불변 2 — 재방문은 스냅샷과 비교한다.** `diff_against_snapshot()` 이 운영시간·입장료 등 달라진 필드를 낸다.
- **실패 시** — 전부 «확인 필요»로 표시되고 일정은 성립한다.

> **예약·티켓은 지금 여기까지다.** A4가 «예약이 필요한가»를 확인해 공식 링크를 담고,
> 앱이 연결한다. 예매 실행 연동(잔여석·결제)은 도구 계층에 어댑터 하나를 더하는 자리로
> 남겨 두었다 — **Agent는 바뀌지 않는다** (UR-39 · Phase 3).

### A5 · Planner — 시간표 계산

| | |
|---|---|
| **입력** | 후보 · 취향 · 이동행렬 · 운영시간 · 날씨 |
| **출력** | `Itinerary` — 항목별 도착·출발·이동수단·선택 이유 |

```
① _meal_slot()        식사는 시간대가 정해져 있다 — 자리를 먼저 잡는다
② _apply_dwell()      체류시간 (말했으면 그 범위, 아니면 과거 평균 배율)
③ _best_leg() ×N      구간별 이동수단
④ _measure_legs()     실측 (예산 허용 범위 안에서)
⑤ _reflow()           측정 결과로 시계를 다시 흘린다
⑥ _reserve_to_dest()  도착지까지 갈 시간 확보
⑦ endpoint_notes()    출발·도착 안내 문구
```

```
score(c) = final_score(c) − travel_min/120 + (10 if 사용자 확정 장소 else 0)
제약      depart ≤ day_end  ∧  운영시간 내  ∧  휴관일 아님
```

- **불변 1 — LLM을 쓰지 않는다.** 시각 계산을 LLM에 맡기면 이동시간과 운영시간을 지어낸다. 재현 가능해야 같은 조건에서 같은 일정이 나온다(NFR-05).
- **불변 2 — 사용자 결정을 뒤집지 않는다.** `+10` 은 «유지»를 고른 장소가 재계획 때 밀려나지 않게 하는 잠금이다. **원칙을 점수 함수 안에 박아 넣었다.**
- **불변 3 — 체류시간은 전체에 같은 배율을 곱한다.** 미술관이 카페보다 오래 걸린다는 사실과 이 사용자가 오래 머문다는 사실은 별개다. 장소별 상대 순서를 보존한다.
- **불변 4 — 하루 끝을 넘기는 항목은 버린다.** 갈 수 없는 일정을 남기지 않는다.
- **실패 시** — 짧은 일정을 준다.

### A6 · Route — 이동 계산

| | |
|---|---|
| **입력** | 좌표쌍 · 선호 이동수단 · 도착지 주차 사정 |
| **출력** | 구간 소요시간 · 수단 · 환승수 · `travel_path`(경로 선형) · `transport_mix` |

**무료 경로 API 3종을 수단별로 나눠 쓴다** — NCP Directions는 자동차만 제공하므로,
도보를 자동차 경로로 계산하면 골목과 보행로를 무시해 실제와 크게 어긋난다.

| 수단 | 제공자 |
|---|---|
| 자동차 | NAVER Directions 5/15 |
| 도보·자전거 | OpenRouteService (Matrix로 N×N 1콜) |
| 지하철·버스 | ODsay LAB (`loadLane`으로 노선 선형까지) |

**최단루트는 시간만 보지 않는다.** 경로 API가 알려주지 않는 비용을 시간으로 환산한다.

```python
PARKING_PENALTY_MIN  = {"none": 15, "nearby": 8, "paid": 3, "free": 0, "unknown": 5}
WALK_PREFERENCE_MIN  = 5   # 5분 차이면 걷는 게 낫다
TRANSFER_PENALTY_MIN = 4   # 환승 1회의 체감 부담
```

- **불변 1 — 명시한 수단은 절대 바꾸지 않는다.** 수단을 섞는 건 `best`(최단루트)일 때뿐이다.
- **불변 2 — 방문 순서는 건드리지 않는다.** 순서는 A5의 책임이다.
- **불변 3 — 추정이면 추정이라고 쓴다.** 측정 불가 시 직선거리 추정으로 내려가되 «(추정)» 을 표시하고, 지도에서도 **옅은 점선**으로 그린다. 지도가 없는 정보를 있는 것처럼 말하면 안 된다.
- **실패 시** — 거리 기반 추정 + «추정» 표시.

### A7 · Gap — 빈틈 채우기

| | |
|---|---|
| **입력** | 편성 중 일정 · `Gap` · 앵커 좌표 · 남은 예산 |
| **출력** | `nearby[]` · 삽입된 식사·카페 항목 |

```
detect_gaps → ⟨Send 팬아웃⟩ nearby_search → rerank_nearby → fill_gaps → _reflow
```

```python
MEAL_WINDOWS = ((11:30, 13:30, "meal"), (17:30, 19:30, "meal"))
```

- **불변 1 — 식사는 자리를 먼저 잡는다.** 나중에 끼워 넣으면 문화 일정이 하루를 꽉 채워 정작 사용자가 말한 식사가 빠진다.
- **불변 2 — 반경은 남은 시간에 비례한다**(60분 미만 500m, 이상 1,200m). «가면 못 돌아오는 추천»을 막는다.
- **불변 3 — 종류별 몫을 지킨다.** «문화 2 + 디저트 3»처럼 사람이 개수를 말하는 단위(그룹)와 저장 단위(`PlaceKind` 7종)가 달라, `KIND_GROUPS`·`kind_quota`가 둘을 잇는다. 못 채운 몫은 **자리를 비워 둔다**.
- **불변 4 — 삽입 뒤에는 반드시 `_reflow()`.** 빠지면 삽입 항목의 시각이 앞뒤와 어긋난다.
- **실패 시** — 빈틈이 빈 채로 남을 뿐 일정은 성립한다.

### A8 · Guardian — 물어볼 것 고르기 (차별점)

**하는 일을 한 문장으로** — 완성된 일정을 6가지로 검사해 문제를 모으고,
그중 **시스템이 알아서 고칠 수 있는 것은 조용히 고치고, 사용자만 결정할 수 있는 것만
확인 카드로 만들어 그래프를 멈춘다.**

| 문제의 종류 | 처리 | 예 |
|---|---|---|
| 자동으로 고칠 수 있다 | 묻지 않고 고친다 | 앞 일정이 5분 늦어 순서를 당기면 해결되는 경우 |
| 사용자만 정할 수 있다 | **카드로 올리고 멈춘다** | 「작년에 주차로 20분 기다린 곳인데 그대로 갈까요?」 |

**묻는 횟수를 줄이는 것이 이 Agent 의 목적이다.** 다 물으면 사용자는 읽지 않고,
안 물으면 AI 가 임의로 바꾼 것이 된다.

| | |
|---|---|
| **입력** | 확정 일정 · `archive_hits[]` · 날씨 · 스냅샷 diff |
| **출력** | `issues[]` · `advisories[]`(확인 카드) · `interrupt()` 정지 |

```
START → ⟨병렬 6종⟩ check_hours · check_travel · check_overlap
                   check_weather · check_revisit · check_friction
      → triage → build_confirm_cards → interrupt() → 사용자 선택
```

| 검사 | 보는 것 |
|---|---|
| `check_hours` | 운영시간 · 휴관일 |
| `check_travel` | 앞 장소에서 시간 안에 닿는가 |
| `check_overlap` | 시각이 겹치는가 |
| `check_weather` | 악천후 시간대의 야외 일정 |
| `check_revisit` | 재방문이라면 달라진 점 |
| `check_friction` | 지난번 불편했던 곳인지 (**UR-40 · 기획안 2.1-②**) |

- **불변 1 — 여섯 검사는 `Issue`만 쌓고 판단하지 않는다.** 검사마다 «이건 물어야 하나»를 정하면 기준이 검사 수만큼 갈린다. 판단은 `triage` 한 곳에 모은다.
- **불변 2 — 올리는 조건은 AND다.** `auto_fixable=False` **이면서** `severity ≥ 2`. OR로 읽으면 사소한 이슈까지 카드가 되어 정작 중요한 경고가 묻힌다.
- **불변 3 — 첫 선택지는 항상 «그대로 진행».** 변경이 기본값이면 사용자는 사실상 자동 변경을 승인하게 된다.
- **불변 4 — 카드 id는 `adv-{kind}-{place}` 로 고정.** `Issue.id`에서 따오면 재계획마다 같은 문제가 새 카드가 된다(실제로 이슈 6건이 카드 21장이 됐다).
- **불변 5 — 카드 이름은 `Issue.place_name`.** `seq`는 재편성으로 흔들리지만 검사 시점에 박은 이름은 흔들리지 않는다.
- **불변 6 — 별점 상한 `_FRICTION_RATING_CEIL = 3.5`.** 4.5점을 주고도 «조금 붐볐다»를 남기는 경우가 흔하다. 그것까지 올리면 진짜 불편이 카드 더미에 묻힌다.
- **실패 시** — 확인 카드 없이 확정하고 «확인 필요» 표시만 남는다.

**카드에는 항상 다섯 가지가 들어간다** — (1) 발견된 문제 (2) 관련 기록·공식정보
(3) 일정에 미치는 영향 (4) 변경 이유 (5) 선택지.

### A9 · Memory — 기록 · 학습

| | |
|---|---|
| **입력** | 확정 카드 선택 · 일정 diff · 방문 기록 |
| **출력** | `plan_edits` 행 · 갱신된 `taste_profiles` · `plans` 저장 |

```
save_itinerary()          →  plans(user_id, plan_date, payload)   ← 캘린더의 쓰기 지점
save_decisions()          →  hitl_decisions
_decision_signals(state)  →  확정 카드에서 고른 것 (drop·replace·reorder·수단변경)
extract_edit_signals()    →  두 일정 버전의 diff
_merge_signals(①,②)      →  같은 사건을 두 번 세지 않는다
save_plan_edits()         →  plan_edits   신호 하나 = 행 하나
rebuild_profile()         →  taste_profiles
```

**신호를 두 갈래로 뽑는 이유** — 처음 만든 일정에서 카드로 장소를 빼면 diff는 아무것도
못 본다. 비교 대상(`current_itinerary`)은 **수정 요청일 때만** 불러오기 때문이다.
사용자가 가장 분명하게 «싫다»고 말한 순간이 하필 그때다.

- **불변 1 — 확정된 뒤에만 배운다.** 검토 중인 일정으로 배우면 사용자가 거절한 것을 학습한다.
- **불변 2 — «그대로 진행»은 신호로 세지 않는다.** 아무것도 안 한 선택에 취향을 부여하지 않는다.
- **불변 3 — 저장하고 끝나면 안 된다.** 재집계가 되읽지 않으면 방문 한 건이 들어오는 순간 프로필이 방문만 보고 새로 만들어져 수정 행동이 지워진다.
- **불변 4 — 저장 실패는 삼킨다.** 개인화는 일정 생성의 전제가 아니다. DB가 죽었다고 이미 만든 일정을 못 보여줄 이유가 없다.
- **실패 시** — 학습만 건너뛰고 응답은 정상.

## 6. 이 문서를 고칠 때

1. **Agent를 더하거나 나눌 때는 §1.1의 세 기준을 먼저 통과시킨다.** 통과하지 못하면 기존 Agent의 내부 함수로 둔다.
2. **§2 표의 출력 채널을 바꾸면 [AGENT_WORKFLOW.md §4](AGENT_WORKFLOW.md)의 데이터 흐름표가 함께 바뀐다.** 한쪽만 고치면 두 문서가 서로 다른 계약을 말하게 된다.
3. **상태 판정은 소스를 다시 읽는다.** 근거 없이 ✅ 를 적으면 이 문서 전체가 근거를 잃는다.
