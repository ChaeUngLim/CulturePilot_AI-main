## 2. 흐름 셋

### 2.1 첫 실행 온보딩 (`FLOW_ONBOARDING`)

```
취향 선호도 ──▶ 자동/수동 분기 ──▶ (수동) 직접 장소 선택하기
                    │                        │
                    └────────▶ 진행 화면 ◀───┘
                                    │
                                    ▼
                            지도 + 타임라인
```

이 흐름이 있는 이유는 **아카이브가 0건인 첫 사용자**다. 방문 기록이 없으면
`personal_score` 가 0.5 로 고정돼 개인화가 사실상 꺼진 채 첫인상이 만들어진다
(`taste-cards.tsx` 주석 · UR-01). 카드로 «말로 밝힌 취향»을 먼저 받는다.

**이미 있는 화면과 겹친다.** `taste-cards.tsx` 의 카드 더미는 카탈로그 카테고리
12장(미술관·박물관·공연장…)이고, 참조 화면은 주제 6장(주요 명소·음식 및 음료…)이다.
둘을 이어 붙이면 첫 실행에 18장이 되어 이탈한다. **주제 6장을 첫 실행에 두고,
카테고리 12장은 「취향」 탭에서 이어 받는다** — 주제는 이번 일정의 조건이고
카테고리는 오래 쓰는 프로필이라, 애초에 수명이 다르다.

### 2.2 AI 일정 추천받기 (`FLOW_AI_PLAN`)

```
1/5 지역 → 2/5 기간 → 3/5 동행자 → 4/5 스타일 → 5/5 밀도
                                                      │
                             POST /chat (conditions_override 한 번에)
                                                      ▼
                                   추천 일정 ──▶ 시작일 선택 ──▶ 최종 일정
```

**다섯 단계를 다 모아 한 번에 보낸다.** 단계마다 서버를 부르면 4단계에서 뒤로
갔을 때 앞 단계 결과가 이미 쓰인 뒤가 되고, 사용자가 보는 화면과 서버가 들고 있는
조건이 갈린다.

「새로운 추천받기」는 **새 `thread_id` 로** 부른다. 같은 스레드로 다시 부르면 앞
결과가 `current_plan` 으로 딸려 들어가 라우터가 `PLAN_MODIFY` 로 분류한다 —
새 추천을 원했는데 기존 일정을 손보는 답이 온다.

### 2.3 직접 일정 만들기 (`FLOW_MANUAL_PLAN`)

```
지역 → 날짜 등록 → 동행자·스타일(한 화면) → Day별 장소 추가 → Day1/Day2 일정
```

동행자와 스타일을 한 화면에 합친 것은 참조 화면 그대로다(`4.동행자 선택.jpg`).
AI 흐름은 5단계로 나누고 직접 흐름은 한 화면에 합치는 차이가 있는데, 직접 흐름을
고른 사용자는 이미 «내가 정하겠다»고 선언한 쪽이라 단계를 늘릴 이유가 없다.

## 3. 선택지 → 서버 필드

선택지의 `writes` 는 **`TripConditions` 필드명 → 값**이다. 앱은 이것을 모아
`POST /chat` 의 `conditions_override` 로 보내고, 라우터
`app/graph/router/enrich.py::_apply_override()` 가 병합한다.
**조건 밖(예: `PlanFlags`)에는 쓸 수 없다** — §4 의 미지원 2건이 그래서 나온다.

### 3.1 주제 (첫 실행)

| 칩 | writes |
|---|---|
| 주요 명소 | `kind_quota={"culture": 1}` |
| 음식 및 음료 | `kind_quota={"food": 1, "cafe": 1}` |
| 박물관 및 문화 | `kind_quota={"culture": 2}` · `interests=["박물관","미술관"]` |
| 공원 및 자연 | `kind_quota={"outdoor": 1}` · `indoor_pref="outdoor"` |
| 쇼핑 | `kind_quota={"shop": 1}` |
| 바 및 야간 활동 | `end_time="22:00"` ⚠ 전용 `PlaceKind` 가 없다 |

`kind_quota` 의 키는 `PlaceKind` 가 아니라 **`schemas.KIND_GROUPS` 의 그룹명**이다
(`culture` `food` `cafe` `shop` `outdoor`). 사람이 «문화 2개»라고 말하는 단위와
저장 단위(`event`/`venue`)가 다르기 때문이다. 여러 칩을 고르면 앱이 같은 키의 값을
**더해서** 보낸다.

### 3.2 동행자

| 칩 | `companions` | 비고 |
|---|---|---|
| 혼자 | `solo` | |
| 친구와 | `friends` | |
| 연인과 | `couple` | |
| 배우자와 | `couple` | 서버에 `spouse` 가 없다. `companion_prefs` 도 `couple` 키로 쌓인다 |
| 아이와 | `kids` | |
| 부모님과 | `family` | |
| 기타 | `unknown` | |

**참조 화면은 「다중 선택이 가능해요」라고 적혀 있지만 단일 선택으로 바꾼다.**
서버 `companions` 는 단일 `Literal` 이라, 다중으로 받으면 마지막 하나만 살아남고
사용자가 고른 것과 달라진다. 다중을 살리려면 스키마를 `list` 로 바꾸고 점수·프로필
양쪽을 함께 고쳐야 하는데, 그건 화면 작업이 아니다.

### 3.3 여행 스타일 → `interests`

`interests` 값은 **`scripts/_catalog_data.py` 의 카테고리 문자열과 글자까지 같아야**
후보 점수에 반영된다. 화면이 «전시»라고 묻고 카탈로그가 «전시관»이면 그 취향은
어떤 후보와도 만나지 못한다 — 화면은 멀쩡히 동작하는데 개인화만 조용히 꺼진다.
`validate()` 가 이 한 가지를 잡으려고 있다.

| 칩 | writes |
|---|---|
| 체험·액티비티 | `interests=["공방"]` |
| SNS 핫플레이스 | `interests=["복합문화공간","갤러리"]` |
| 자연과 함께 | `interests=["야외공연장","거리"]` · `indoor_pref="outdoor"` |
| 유명 관광지는 필수 | `interests=["문화유산","박물관"]` |
| 여유롭게 힐링 | `interests=["도서관","독립서점"]` · `dwell_min=60` |
| 문화·예술·역사 | `interests=["미술관","박물관","공연장","문화유산"]` |
| 여행지 느낌 물씬 | `interests=["거리","문화유산"]` |
| 쇼핑은 열정적으로 | `interests=["복합문화공간"]` · `kind_quota={"shop": 2}` |
| 관광보다 먹방 | `kind_quota={"food": 2, "cafe": 1}` |

### 3.4 일정 밀도

| 칩 | writes |
|---|---|
| 빼곡한 일정 선호 | `stop_count=6` · `dwell_max=60` |
| 널널한 일정 선호 | `stop_count=3` · `dwell_min=90` |

### 3.5 지역

참조 화면은 「가평·양평」·「통영·거제·남해」처럼 **생활권 묶음**이다. 이 백엔드의
지역 판정(`app/tools/region.py`)은 **시·도** 단위라, 묶음 칩을 그대로 쓰면 어느
시·도로 보낼지 화면이 임의로 정하게 된다. 그래서 시·도 17개로 편다.

로컬 카탈로그가 실제로 담고 있는 곳은 **5개 시·도 92곳**이다:

| 시·도 | 카탈로그 | 나머지 |
|---|--:|---|
| 서울 (강남·서초·송파·용산·서대문) | 52 | 한국문화정보원 API + 카카오 로컬 |
| 인천 · 부산 · 대전 · 대구 | 각 10 | 〃 |
| 그 밖 12개 시·도 | 0 | **외부 API 응답에만 의존** |

카탈로그는 외부 API가 전부 실패해도 결과가 0건이 되지 않게 바닥을 받치는 레인이다
(`discovery` 의 `search_catalog`). 카탈로그가 없는 시·도는 그 바닥이 없다는 뜻이라,
칩에 그 사실을 적어 둔다.

## 4. 옮기지 않는 것 8건

지우지 않고 `supported=False` 로 남긴다. 목록에서 지우면 «없다»가 아니라
«원래 없었다»로 읽혀, 기획안과의 차이를 추적할 수 없게 된다.

| # | 선택지 | 참조 화면 | 왜 길이 없나 | 열려면 |
|:--:|---|---|---|---|
| 1 | 과거 여행에서 배우기 (토글) | 첫 실행 1 | `PlanFlags.use_archive` 는 라우터가 정한다. `conditions_override` 는 `TripConditions` 만 병합한다 | `ChatRequest` 에 플래그 필드 추가 |
| 2 | 하루를 채울 추가 장소 (토글) | 첫 실행 2 | `PlanFlags.nearby_fill` — 위와 같은 제약 | 〃 |
| 3 | 해외 도시 | AI 1/5 · 직접 지역 | 탐색 소스가 한국문화정보원 API·카카오 로컬·국내 카탈로그뿐. `region.py` 도 국내 시·도 표만 갖는다 | 해외 소스 도입 (범위 밖) |

### 다일정(Day 1 / Day 2)에 대해

참조 화면 `1 Day 2 Day 일정 최종 화면.jpg` 와 `10.최종 일정 완료 화면.jpg` 는
day1·day2 를 한 화면에 쌓아 보여 준다. 이 앱의 `Itinerary` 는 날짜 하나 · 항목
목록 하나이므로, **지금 구조에서 다일정은 화면 문제가 아니라 스키마 문제다.**

지금 손대지 않고 흉내 내려면: 날짜별로 `POST /chat` 을 n+1 회 돌리고
`GET /plans/{user_id}?from=&to=` 로 묶어 화면에서만 day 로 나눈다. 구간 거리·경로
최적화는 **날짜 안에서만** 돈다는 사실이 그대로 드러나므로(day1 마지막 → day2 첫
장소 사이에 선이 없다), 화면에서 그 경계를 숨기지 말고 그대로 보여야 한다.

## 5. 디자인 토큰

`app/ui.py` 의 `COLORS`·`RADIUS`·`SPACE_UNIT`·`TYPE_SCALE` 은
`mobile/src/theme.ts` 와 **같은 값**이다. 서버가 화면 명세를 내릴 때 색까지 함께
내려야 앱이 임의로 해석하지 않는다.

**참조 화면의 색은 가져오지 않는다.** 캡처의 배경은 흰색/살구빛 그라데이션이고
강조는 `#FF5A3C`(주황)·`#3B82F6`(파랑)인데, 이 앱은 `colors.bg` 가 `#0F1115` 인
어두운 화면이다. 밝은 배경 전제의 강조색을 그대로 얹으면 본문 대비가 무너진다.
가져오는 것은 **레이아웃과 단계 구성**이지 팔레트가 아니다.

| 역할 | 참조 화면 | 이 앱 |
|---|---|---|
| 배경 | 흰색 / 그라데이션 | `bg #0F1115` |
| 강조 · 주 버튼 | `#FF5A3C` / `#3B82F6` | `accent #7C9CF5` |
| 선택된 칩 | 파란 테두리 + 파란 글자 | `accentSoft #243049` 배경 |
| 카드 | 흰 배경 + 그림자 | `surface #171A21` + `border #2A2F3A` |

간격 단위는 4px 다 (`space(3)` = 12px). 모서리 반경은 `sm 8 / md 12 / lg 16 / xl 22`.

## 6. 진행 화면

참조 화면 `3.자동 또는 수동 선택 후 화면.jpg` 는 5줄과 「⏱ ~20초 남음」을 보여준다.
그 5줄은 이 앱의 노드와 1:1이 아니다.

| 참조 문구 | 실제 노드 |
|---|---|
| 여행을 생성 중입니다 | `classify` |
| 선호 설정 적용 중 | `archive` |
| N곳 지도에 표시 중 | `discovery` |
| 빈틈 채우기 | `itinerary` (`subgraphs/itinerary/gaps.py`) |
| 경로 최적화 중 | `itinerary` (`routes.py` · `legs.py`) |

**화면에는 참조 문구가 아니라 실제 노드 라벨을 쓴다.** 없는 단계를 미리 그려 놓으면
진행 표시가 멈춘 것처럼 보이는 순간이 반드시 온다. 라벨 표는
`mobile/src/hooks/useCultureMate.ts` 의 `NODE_LABEL` 과 같아야 하고,
`app/ui.py::PROGRESS_STAGES` 가 그 사본이다.

**「~20초 남음」은 쓰지 않는다.** 실측 응답 중앙값은 5.1초다(HANDOFF §1, NFR-01
상한 15초). 20초를 적어 놓고 5초에 끝나면 사용자는 카운터를 신뢰하지 않게 되고,
반대로 외부 API가 느린 날에는 0초에서 멈춘 카운터를 보게 된다. 남은 시간을 세는
대신 **도착한 노드를 그린다** — `ProgressTrace` 가 이미 그렇게 한다.

## 7. 적용 순서

이미 있는 것 위에 얹는다. 새로 만드는 화면보다 **겹치는 화면을 정리하는 쪽이 먼저**다.

| 순서 | 할 일 | 손대는 곳 | 새 의존 |
|:--:|---|---|:--:|
| 1 | 명세 정합성을 테스트로 못 박는다 | `tests/test_ui_spec.py` (신규) — `assert app.ui.validate() == []` | 없음 |
| 2 | 명세를 앱에 내린다 | `app/api/main.py` 에 `GET /ui/spec` 추가 → `app.ui.spec()` | 없음 |
| 3 | 취향 카드를 주제 6장 + 카테고리 12장으로 나눈다 | `mobile/app/taste-cards.tsx` (§2.1) | 없음 |
| 4 | AI 5단계 위저드 화면 | `mobile/app/plan-wizard.tsx` (신규) · `RegionPicker` 재사용 | 없음 |
| 5 | 생성 바텀시트 (직접/AI 분기) | `mobile/app/(tabs)/calendar.tsx` 의 ＋ 버튼 | 없음 |
| 6 | 진행 화면 전체화면 승격 | `ProgressTrace.tsx` 확장 | 없음 |
| 7 | 미지원 1·2 (아카이브·빈틈 토글) | `app/api/schemas.py::ChatRequest` 에 플래그 필드 | 없음 |
| 8 | 다일정 | 스키마 변경. §4 참고 — **화면 작업이 아니다** | — |

1·2번을 먼저 하는 이유는, 그 둘이 끝나면 3번 이후에서 화면과 서버가 갈리는 순간
**테스트가 먼저 깨지기** 때문이다. 순서를 뒤집으면 화면을 다 만든 뒤에 어긋남을
발견하게 된다.

## 8. 검증

```bash
docker exec culturemate python -m app.ui
```

`✅ 화면 명세와 서버 스키마가 정합하다` 가 나오고, 이어서 미지원 선택지 8건이
이유와 함께 출력된다. 어긋난 것이 있으면 `❌ 불일치 N건` 과 함께 **전량**을 목록으로
돌려준다 — 첫 번째에서 멈추면 고칠 때마다 다시 돌려야 한다.

`validate()` 가 잡는 것:

1. `writes` 의 키가 `TripConditions` 에 실제로 있는가
2. `Literal` 필드에 쓰는 값이 그 집합 안에 있는가 (`companions` · `transport` · `indoor_pref`)
3. `kind_quota` 의 키가 `KIND_GROUPS` 에 있는가
4. `interests` 값이 카탈로그 카테고리에 있는가 ← **§3.3 의 조용한 고장**
5. 라벨 표가 서버 `Literal` 과 **같은 집합**인가
6. 한 단계 안에서 선택지 id 가 유일한가

`validate()` 가 잡지 못하는 것: 색 값이 `theme.ts` 와 갈리는 것, `PROGRESS_STAGES`
가 `NODE_LABEL` 과 갈리는 것. 둘 다 TS 쪽 값이라 파이썬에서 읽을 수 없다 — 눈으로
맞추거나, 필요해지면 `tests/` 에서 `theme.ts` 를 파싱해 대조한다.
